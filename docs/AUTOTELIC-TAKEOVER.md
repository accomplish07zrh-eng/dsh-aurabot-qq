# 浏览模块接管方案 · v1（自驱引擎的配套设计）

> 上游文档：`docs/AUTOTELIC-PLAN.md`（实施方案 v3）、`docs/AUTONOMY-NOTES.md`（讨论结论）。
> 本文只讲一件事：**自驱引擎如何接管浏览型模块（douyin / bili）的自主循环与兴趣决定权**。
> 主方案不重复这些内容，实现时两份一起看。
>
> 基线：`local/runtime` @ `4c362d0`；本机配置实测（douyin/bili `autoBrowse: true`，
> `maxRunsPerDay: 11`；tophub `tourTimes: 09:30,21:00`）。
>
> **主人定的两条口径（2026-11-04）**：
> 1. 一键关闭**不自动做**——面板提供按钮，**主人手动点**；
> 2. 接管的除了自主循环，还有**「兴趣」部分**——刷什么、什么有意思，这个决定权归主动引擎。
>
> **修订（2026-11-05，主人指出）**：§10 兼容设计重写——**不依赖任何模块开发标准**，
> 通用接口改为**模型会话流**（聊天流水/记忆/activity），约定类做法降级为顺手优化。

---

## 0. 一句话

> 模块只剩**手**（平台机器 / cookie / 浏览器），
> **脑**（什么时候刷、看什么、什么值得说）归自驱引擎。

## 1. 为什么接管

浏览型模块是旧模型的活化石：「定时干活 → 干完强行私聊汇报」——
`outbound-policy` 当初就是为堵它们造的。与散养模型的冲突：

| 冲突 | 说明 |
| --- | --- |
| **两套意志** | 主人定过「攒着评、可以不说」，而模块还在按自己的钟点跑、按自己的意愿汇报 |
| **token 双花** | 每轮内部都走 `api.think`；autotelic 上线后同一份好奇心花两遍钱 |
| **素材不欠它们** | purpose 的素材池是「聊天流水 + 记忆 + rss-reader」，抖音/B站**不直接喂** purpose |

**但模块本体必须留**——它们封装了重新写一遍非常贵的东西：
平台 cookie / 登录态、浏览器自动化、限速与防风控（`douyin.gate`）。

## 2. 脑和手的分工

| | 接管前（模块自治） | 接管后（autotelic 主导） |
| --- | --- | --- |
| 什么时候刷 | 模块自己的闹钟（`intervalHours: 1`，一天 11 轮） | 她好奇了才刷 |
| 看什么 | 模块的关键词/筛选（`keywords: ['自己决定']`、`minViews`、`maxAgeDays`） | **好奇评分挑出来的目标** |
| 看完怎么办 | 模块自己决定私聊分享（`share` 上限 10/天） | 好奇够就立项，攒着评 |
| 模块的角色 | 脑 + 手 | **只剩手** |

模块里的 `keywords` / `minViews` / `shareBias` 这些「兴趣配置」在接管期间**退役不用**
（不是删掉——主人哪天关掉 autotelic，它们自动回来）。

## 3. 按钮行为（下一增量实现；引擎本体已提交，接管尚未做）

面板（autotelic 设置页）一个开关：「**接管浏览模块**」。**主人手动点，不自动。**

```
点下：
  1. 备份 douyin.autoBrowse / bili.autoBrowse 的原值 → ext.autotelic.takenOver
  2. 把它们压制成 false（直接写 config——这些模块每次运行都现读 settings，立即生效）
  3. 压制 tophub 的主动分享（shareLimit → 0）；巡游保留（它是便宜素材源）
  4. 面板展示接管状态

再点（还原）：
  按 takenOver 里的备份原值写回，删除备份记录
```

**范围**：

| 模块 | 处置 | 理由 |
| --- | --- | --- |
| `douyin` | 压 `autoBrowse` | 11 轮/天太重；分享是真账号行为 |
| `bili` | 压 `autoBrowse` | 同上；内容等她好奇了再看 |
| `tophub` | **保留巡游**，只压分享 | 便宜素材源，解决「好奇需要素材喂」的冷启动 |
| `purpose` / `speakup` | **不动** | 陪聊归 purpose（主人已定） |
| `phone` / `mijia` | 不动 | 手动域 |
| `heybox` / `tieba-reader` | 不动（已关） | — |

**铁律：不关模块总开关（`enabled`）。** 关了总开关，`api.use('douyin')` 就拿不到了——她的手断了。

## 4. 兴趣接管的具体形态（P2 核实点）

她立项「看看B站游戏区有什么新东西」之后：

```
好奇评分立项 → api.use('bili') 的浏览/搜索入口 → 拿回一批条目
  → autotelic 用好奇评分自己挑 → 值得的进账本 → 攒够或满一天才评要不要说
```

模块的 `keywords` 筛选全程**不参与**——筛选权在 autotelic。

**P2 核实点**：douyin / bili 的导出面有没有「定向浏览」入口（指定看哪类内容）。

- 有 → 直接用；
- 没有 → 退一档：用模块的**通用浏览**拿回条目，autotelic 自己筛。功能等价，多筛一步。

**首期建议从 bili 开始**（纯浏览、无写操作、内容质量高），douyin 第二个接。

## 5. 边界情况（三条都要处理）

**① 主人手动又把 `douyin.autoBrowse` 打开怎么办？**

接管期间**每分钟压一次**（tick 里顺手检查，发现被打开就压回去），面板明示
「接管期间此开关无效」。理由：主人定的口径是「不能用户自己去关闭」——接管期间这个键归 autotelic 管。

**② 中途崩溃 / 插件重启（2026-11-05 主人定：**恢复接管**）。**

备份在 `ext.autotelic.takenOver`（落盘）。启动时先查：**上次接管仍有效**（备份存在）→
**重新压制**（备份还在、值没变，直接再 apply 一遍），接管状态跨重启持久。

理由：接管是一次性的职责移交，不是临时开关——插件重启不该让它悄悄失效。
「等主人再点」的只有**第一次**启用；还原（关掉接管）才需要主人再点。

实现要点：
- setup 时：`takenOverBackup` 非空 → 逐键**重新压制**（幂等，压了也不出错）；
- dispose 时：**不还原**（插件卸载≠主人关接管；还原只走按钮）；
- 只有面板按钮「关掉接管」才写回原值并清空备份。

**③ 面板透明。**

`/autotelic/status` 返回接管状态与原值：

```jsonc
{ "takenOver": { "douyin": { "autoBrowse": "已压制（原 true）" },
                 "bili":    { "autoBrowse": "已压制（原 true）" } } }
```

不透明的话，主人会以为模块坏了。

## 6. 接管动作本身要进审计

与「她判断不必告诉主人也要记录」是同一条逻辑：**管控动作也是记录**。
审计日志里要有：`{ at, action: 'takeover-on' | 'takeover-off', targets: ['douyin','bili'] }`。

## 7. 验收场景

| # | 场景 | 期望 |
| --- | --- | --- |
| 1 | 不点按钮 | douyin/bili 行为与从前**逐字一致**（autoBrowse 照跑） |
| 2 | 点下接管 | `douyin.autoBrowse=false`、`bili.autoBrowse=false`；原值在 `takenOver` 里 |
| 3 | 接管中主人手动改回 true | 60 秒内被压回 false；审计里有一条压制记录 |
| 4 | 再点还原 | 原值写回；模块行为恢复 |
| 5 | 接管中崩溃重启 | 启动时检测到备份仍有效 → **重新压制**（幂等）；接管状态跨重启持久。只有主人点「还原」才回到接管前 |
| 6 | 接管中 autotelic 立项看B站 | 走 `api.use('bili')`，条目由好奇评分筛选；模块 `keywords` 不参与 |
| 7 | 审计 | 接管/还原各有至少一条记录 |

## 10. 兼容后期第三方模块（2026-11-05 主人修正：靠模型会话，不靠约定）

> **主人原话**：「我们无法控制其他模块开发标准。目前的标准无法替代以后的。可以借助模型会话来实现功能。」
>
> 这条**推翻了 v1 的 §10**——阿娘原先押在两个约定上（`autoBrowse` 键名、`seen` 事件），
> 但**约定是我们求别人守的，别人不守我们一点办法没有**。会话流才是我们自己的地盘。

### 10.1 通用接口是「会话流」，不是任何模块约定

不管模块守不守任何标准，它们做了什么都**最终汇进三 条我们完全控制的通道**：

| 通道 | 什么会出现在这里 | 为什么零约定依赖 |
| --- | --- | --- |
| **聊天流水**（`hub.chatLogOf`，`hub.js:359`） | 模块分享的内容**本来就是发到 QQ 聊天里的消息**——抖音分享、B站推荐、热榜速递，全是 chatId 里的普通消息 | 分享给主人是这些模块**存在的目的**，它们别无出口 |
| **记忆库**（`memory.list` / `addEvent`） | 模块按约定写的 `seen` 只是其中一种来源；聊天摘要、她自己的经历都在 | 约定是加分项，不是门槛 |
| **activity 事件**（`api.on('activity')`） | 所有进出消息的元数据（谁、哪、发了没） | 宿主层事件，模块管不着 |

purpose 的素材采集**本来就是这么干的**（`purpose/module.js:155` 直接读 `hub.chatLogOf`）。
**模块分享一条抖音视频 → 那就是聊天流水里的一条普通消息 → autotelic 的感知层自然吃到。**
模块守不守 `seen` 约定、键名叫什么，**根本无关紧要**。

### 10.2 判断权在模型会话本身

好奇评分**本来就是一次模型调用**（便宜模型自评「我对这个已知多少」）。
模型读到的输入是会话流（上面的三条通道），**不需要任何模块提供结构化字段**：

- 模块的关键词筛选只决定「什么**进入**她的世界」；
- **进入之后，什么有意思、值不值得深挖，判断权 100% 在她的会话里**——
  这就是「兴趣接管」的真正完成态：不是去改模块的筛选逻辑，而是**她自己在会话里重新审判一切**。

### 10.3 行动权也不依赖模块导出面

她想看更多，三条路，全都不经过第三方模块的代码：

| 路 | 依赖 |
| --- | --- |
| **L0 `fetch` 直接到网上看**（B站/抖音都有公开网页） | 无——这条最彻底：**她的好奇不需要任何模块当眼睛** |
| P3 Python 脚本（独立子进程） | 无 |
| 提案（「给 autotelic 接个 XX 模块」） | 主人批 |

### 10.4 修正后的分层（v1 的「三层兜底」降级为「顺手优化」）

| 层 | 定位 | 依赖约定？ |
| --- | --- | --- |
| **① 会话流感知（本节）** | **主通道，兼容性全靠它** | ❌ 零约定 |
| ② `seen` / `autoBrowse` 约定 | 顺手优化：守了就多一份结构化素材、压制更精准 | 是——所以**只是加分项** |
| ③ 面板手动补条目 | 对不守约定的模块做压制时的兜底 | 否 |

**推论一**：压制按钮（§3）的定位要修正——它是**成本控制**（防 token 双花、防强行私聊），
**不是兼容性依赖**。模块不守约定，她照样能感知世界，只是账本上少一条压制记录而已。

**推论二**：模块的关键词决定了「她的世界里流过什么」，这看似还是门槛——
但她有 `fetch`，**可以直接越过所有模块到公开网页上看**。
这才是散养的彻底形态：**她的好奇不需要任何模块当眼睛，模块顶多算便利。**

### 10.5 v1 → v3 修订对照

| v1 说法（已废） | v3 说法 |
| --- | --- |
| 「`autoBrowse` 是家族约定，探测式压制零改动兼容」 | 约定只是压制动作的**便利启发式**，兼容性不押在它上面 |
| 「`seen` 事件是全市场统一的兴趣数据接口」 | `seen` 只是记忆库的一种来源；**会话流才是主通道** |
| 「守约定的模块零改动就能成为素材源」 | **所有**模块的产出（只要发到聊天/写进记忆）都天然是素材源，守不守约定无关紧要 |
| 「不接管，只喂养」 | 「喂养」依然成立，但通道是会话流，不依赖 `seen` |
